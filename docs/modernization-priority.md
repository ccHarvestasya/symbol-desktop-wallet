# Symbol Desktop Wallet 近代化計画

- 文書状態: 個人メンテナンス中
- 公式提出: 未提出
- 作成日: 2026-09-08
- 最終更新日: 2026-09-08

## 1. 目的と前提

Symbol Desktop Wallet の保守性と秘密情報の保護を段階的に改善する。公式リポジトリへの提案は、コアメンバーのレビュー負荷と既存ユーザーの復旧リスクを抑えるため、目的が明確な複数のPRに分ける。

ただし、PRを細切れにして全体の意図が見えなくならないようにする。各PRは、レビュー可能な範囲で一つの成果が完結した、意味のある変更単位とする。

この資料は親リポジトリの管理資料であり、アプリケーションの実装変更は `desktop-wallet/` 内で行う。

## 2. 文書の扱い

現在は自分用のメンテナンス計画として、実装状況、調査結果、判断理由、未解決事項を記録する。最終的には、公式リポジトリへのIssueやPRで参照できる資料に整える。

公式提出前には、個人的な作業メモを整理し、次の内容を明確にする。

- 変更の背景と解決したい問題
- 対象範囲と対象外の範囲
- 既存データおよび既存ユーザーへの互換性
- セキュリティ上の根拠と採用しなかった案
- テスト結果と再現手順
- PR分割の理由と各PRの受け入れ条件
- コアメンバーに確認したい論点

個人用の仮説や未確認の数値は、確定事項と混同しないように「要確認」「仮案」などの状態を付ける。秘密情報、実ユーザーのデータ、非公開の認証情報は記載しない。

## 3. 対象範囲

### 対象

- プロファイルのニーモニック暗号化
- 通常アカウントの秘密鍵暗号化
- リモートおよびVRF秘密鍵の暗号化
- プロファイルパスワードの検証方式
- パスワード変更、紙ウォレット、暗号化QRの互換性
- 暗号化データの保存形式、移行、復旧テスト
- 依存関係、実行環境、テスト基盤の段階的な近代化

### 対象外

- Symbolネットワークのプロトコル変更
- 秘密鍵そのものの生成・署名アルゴリズムの変更
- 公式リポジトリの運用方針を事前に確定すること
- 既存ユーザーのデータを一括削除または強制移行すること

## 4. 調査時点の現状

調査時点: 2026-09-08

- 親リポジトリ HEAD: `e225046`
- `desktop-wallet` HEAD: `117e9c17`（`dev`、v1.2.0相当）
- 主な構成: `symbol-sdk` 2.0.6、Vue 2、TypeScript 3.7、Electron 11系
- データ保存先: 主に `localStorage`
- 主な保存領域: `ProfileModelStorage`、`AccountModelStorage`、`HarvestingModelStorage`
- `Crypto.encrypt/decrypt` の本番コードでの利用: 13ファイル、29箇所

SDK 2.0.6のプロファイル・秘密鍵向け暗号処理は、次の形式である。

- 16バイトのsalt
- 16バイトのIV
- PBKDF2 1,024回
- AES-256-CBC、PKCS#7
- 暗号文に認証タグがなく、改ざん検知がない

したがって、主な問題はAESの鍵長ではなく、パスワードからの鍵導出コストが低いことと、認証付き暗号ではないことである。

また、プロファイルのパスワード検証値は、saltなしのSHA3-512を1回適用した値である。該当箇所は `src/services/ProfileService.ts` の `getPasswordHash()` と `ProfileModel.password` である。

暗号化データの形式を変更すると、プロファイルのニーモニック、アカウント秘密鍵、リモートおよびVRF秘密鍵、バックアップ出力、パスワード変更処理のすべてに影響する。既存暗号文を読めなくする変更は、通常のデータベースマイグレーションより重大である。

## 5. 主なリスク

| リスク | 影響 | 対応方針 |
|---|---|---|
| 鍵導出コストが低い | 弱いパスワードへの総当たり耐性が低い | コストを測定した新しいKDFへ移行する |
| CBCに認証がない | 保存データの改ざんを検知できない | 認証付き暗号を採用する |
| パスワード検証にsaltがない | 保存データ漏えい時に辞書攻撃を受けやすい | salt付き・コスト付きの検証形式へ移行する |
| SDKの暗号処理が多数の画面に分散 | 変更漏れとレビュー範囲の拡大 | ウォレット側の暗号境界へ集約する |
| 旧データとの互換性が不明確 | ユーザーが資産へアクセスできなくなる | 旧形式を読み取り、新形式へ遅延移行する |

## 6. 優先順位

### P0: 仕様固定と回帰防止

ユーザー向け動作を変える前に、既存形式、互換性、失敗時の挙動を固定する。

- 既存暗号形式の仕様とテストベクトルを整理する
- 誤パスワード、改ざん、破損、空データの期待動作を定義する
- 移行失敗時に旧データを保持する方針を決める
- 実ユーザーデータを使わない復旧テストの方法を決める

### P1: ウォレット側の暗号基盤

SDKの `Crypto` をアプリケーション全体から直接呼ばず、ウォレット側の `WalletCrypto` 相当の境界へ集約する。

新形式はバージョン付きエンベロープとし、少なくとも次の情報を明示する。

```text
version / KDF / KDF parameters / salt / nonce(or IV) / ciphertext / authentication tag
```

KDFは、対象となるブラウザ・Electron・Node環境で利用できることを確認したうえで選定する。候補はArgon2idと認証付き暗号の組み合わせを第一候補とし、共通実装が難しい場合は、十分に調整したPBKDF2-HMAC-SHA-256とAES-GCMなどを代替候補とする。回数やメモリ量は、対象端末での測定結果を根拠に決める。

### P2: 秘密情報の段階移行

漏えい時の被害が大きい順に、秘密情報を種類ごとに移行する。

1. プロファイルのパスワード検証値とニーモニック
2. 通常アカウントの秘密鍵
3. リモートおよびVRF秘密鍵
4. パスワード変更、紙ウォレット、暗号化QR

### P3: 実行基盤の近代化

暗号移行と混ぜず、次の順で別テーマとして扱う。

- 依存関係の監査と、挙動変更を伴わない脆弱性修正
- Node.jsおよびElectronのサポート版更新
- TypeScript、Vue、テスト、Lint基盤の更新
- `localStorage` 依存の縮小と、Electron環境での安全な永続化方式の検討

## 7. PRの分け方

### 基本方針

- 各PRは、一つのレビュー目的と一つの成果を持つ。
- 成果を成立させるためのテスト、移行処理、ドキュメントは同じPRに含める。
- 関連するPRはテーマ群としてまとめ、最初のIssueまたはPRで全体像を示す。
- 後続PRは、テーマ群、前提PR、受け入れ条件を相互参照する。
- 暗号方式変更、データ移行、Electron更新、UI改善のようにレビュー観点が異なる変更は混ぜない。
- 一つのファイルだけを変更すること自体を目的にせず、レビュー可能な意味のある塊にする。

### PR候補

| 区分 | 内容 | 示す成果 |
|---|---|---|
| 0 | Issueと設計メモ | 背景、脅威モデル、互換性、未決定事項を共有する |
| 1 | 暗号基盤 | 旧形式のテスト、`WalletCrypto`、新しい暗号文形式を整える |
| 2 | プロファイル保護 | パスワード検証値とニーモニックを新形式へ移行する |
| 3 | アカウント保護 | 通常アカウントの秘密鍵を新形式へ移行する |
| 4 | Harvesting鍵保護 | リモートおよびVRF秘密鍵を新形式へ移行する |
| 5 | バックアップ互換性 | パスワード変更、紙ウォレット、暗号化QRを移行後も利用可能にする |
| 6 | 実行基盤 | 依存関係、CI、Node.js、Electronなどをテーマごとに更新する |

各PRの差分が大きくなり、独立した受け入れ条件を持つ場合だけ、同じテーマ群の中でさらに分ける。反対に、テストや移行処理を分離すると変更の意図が見えなくなる場合は、一つのPRにまとめる。

## 8. 移行の必須条件

- 旧形式の既存データを、バックアップなしに破壊しない。
- 旧形式を読み取り、新形式で保存できるようにする。
- ログインまたはアンロック成功後など、安全に復号できた時点で遅延移行する。
- 新形式への保存に失敗した場合は、旧データを保持する。
- パスワード変更では、ニーモニック、全アカウント、リモートおよびVRF鍵を取りこぼさない。
- 誤パスワードや認証タグ不一致の場合は、秘密情報を返さず、改ざんを成功扱いにしない。
- 復号した秘密情報をログ、例外、診断データに出さない。
- 既存形式の読み取りを削除する場合は、リリースノートとユーザー向け移行手順を用意する。

## 9. 受け入れ条件

各実装PRでは、対象範囲に応じて次を確認する。

- 暗号化、復号、改ざん検知、誤パスワードの専用テスト
- 旧形式から新形式への移行テスト
- 移行失敗時の旧データ保持テスト
- 再起動後の復号テスト
- パスワード変更後の全秘密情報の復号テスト
- 復号した秘密情報がログに出ないことの確認
- `desktop-wallet` 側の対象テスト、Lint、型チェック、ビルド
