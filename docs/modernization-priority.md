# Symbol Desktop Wallet 近代化の優先順位

- 文書状態: 個人メンテナンス中（公式未提出）
- 調査・更新日: 2026-09-08
- 検証対象: 親リポジトリ `aa983b5`、`desktop-wallet` `117e9c17`（`dev`）

## 1. 目的

Symbol Desktop Wallet の秘密情報保護と保守性を、既存ユーザーの復旧可能性を損なわず段階的に改善する。

公式リポジトリへの提案は、最初に全体像をIssueで共有し、その後、一つの成果が完結する単位でPRに分ける。暗号方式、データ移行、実行基盤の更新はレビュー観点が異なるため、同じPRに混在させない。

この文書は親リポジトリの管理資料である。アプリケーションの変更は `desktop-wallet/` で行う。

## 2. 確認済みの現状

### 構成と保存先

- アプリケーションのバージョンは `1.2.0`。
- `package-lock.json` で解決される主なバージョンは、`symbol-sdk` 2.0.6、Vue 2.6.10、TypeScript 3.7.2、Electron 11.5.0。
- `ProfileModelStorage`、`AccountModelStorage`、`HarvestingModelStorage` は、`SimpleObjectStorage` を介して JSON を `localStorage` に保存する。
- 保存対象には、プロファイルのパスワード検証値と暗号化ニーモニック、通常アカウントの暗号化秘密鍵、Harvesting の暗号化リモート秘密鍵・VRF秘密鍵が含まれる。

### 暗号処理

- `src/` では `Crypto.encrypt()` または `Crypto.decrypt()` を13ファイル、29呼び出し箇所で直接使用している。
- `ProfileService.getPasswordHash()` は、パスワードにsaltを付けず、SHA3-512を1回適用した値をプロファイルへ保存する。
- `symbol-sdk` 2.0.6の `Crypto` は、16バイトのsaltと16バイトのIV、PBKDF2 1,024回、AES-256-CBC（PKCS#7パディング）を使用する。
- この暗号文には認証タグがなく、暗号文の完全性を暗号方式自体では検証できない。

したがって、主な問題はAESの鍵長ではなく、パスワードからの鍵導出コストが現在の用途には低いこと、認証付き暗号ではないこと、暗号処理が画面やサービスに分散していることである。

### パスワード変更の既知の不整合

`FormProfilePasswordUpdate.onAccountUnlocked()` は、プロファイルのニーモニックと、プロファイルに属する通常アカウントの秘密鍵を新しいパスワードで再暗号化する。

一方、`HarvestingModelStorage` の `encRemotePrivateKey` と `encVrfPrivateKey` は再暗号化しない。このため、保存済みのHarvesting鍵がある状態でパスワードを変更すると、新しいパスワードでは当該鍵を復号できず、古いパスワードとの不整合が残る可能性がある。

また、プロファイルを先に保存してからアカウントを順番に更新しており、処理全体は原子的ではない。途中で失敗した場合、旧パスワードと新パスワードの暗号文が混在し得る。

これは将来の暗号方式更新とは独立した、現行データの復旧可能性に関わる問題として扱う。

## 3. 対象範囲

### 対象

- パスワード変更処理の整合性と失敗時の復旧
- プロファイルのニーモニックとパスワード検証値
- 通常アカウント、リモートアカウント、VRFアカウントの秘密鍵
- 暗号化データの保存形式、互換読み取り、移行、バックアップ、復旧
- 紙ウォレットおよび暗号化QRとの入出力互換性
- 依存関係、Node.js、Electron、TypeScript、Vue、テスト・Lint基盤の段階的更新

### 対象外

- Symbolネットワークのプロトコル変更
- 鍵生成方式または署名アルゴリズムの変更
- 既存データの一括削除や、復旧経路のない強制移行
- この文書だけで公式リポジトリの方針を確定すること

## 4. 優先順位

### P0: 現行形式の保全とパスワード変更の修正

新しい暗号方式を導入する前に、現行データを失わない基準を作り、確認済みの不整合を解消する。

1. 現行暗号文の仕様、代表的なテストベクトル、利用箇所を固定する。
2. 誤パスワード、破損、空値、途中失敗時の期待動作をテストで定義する。
3. パスワード変更時に、ニーモニック、対象となる全アカウント鍵、リモート鍵、VRF鍵を一貫して更新する。
4. 途中失敗時に旧データを復元できる更新手順を設計する。
5. 実ユーザーデータを使用しない復旧テストを追加する。

### P1: ウォレット内の暗号境界

SDKの `Crypto` を各画面から直接呼び出さず、ウォレット側の単一の暗号サービスへ集約する。最初は現行形式を同じ結果で読み書きする薄い境界とし、方式変更とは分離する。

境界には、形式の判別とバージョン管理、暗号化・復号・パスワード検証、エラーの正規化、移行要否の判定、秘密情報をログや例外メッセージへ含めない保証を持たせる。

### P2: バージョン付き認証暗号への移行

新形式は、暗号文だけで方式とパラメータを判別できるバージョン付きエンベロープとする。

```text
version / KDF / KDF parameters / salt / cipher / nonce / ciphertext / authentication tag
```

方式とパラメータは実装前に確定しない。対象となるWeb版、Electron、Node.js、および低性能端末で、利用可能性、処理時間、メモリ消費、配布物への影響を測定して選ぶ。

- 第一候補: Argon2idと認証付き暗号
- 代替候補: 十分な反復回数のPBKDF2-HMAC-SHA-256とAES-GCM

新形式はまず新規保存へ適用し、旧形式は互換読み取りを維持する。復号成功後の遅延移行を基本案とするが、保存途中の失敗から確実に復旧できることを採用条件とする。

### P3: 秘密情報ごとの段階移行

暗号基盤の導入後、保存場所と利用経路ごとに移行する。

1. プロファイルのパスワード検証値とニーモニック
2. 通常アカウントの秘密鍵
3. Harvesting のリモート秘密鍵とVRF秘密鍵
4. パスワード変更、バックアップ、紙ウォレット、暗号化QRの入出力

各段階で旧形式の読み取り、再起動後の復号、移行失敗時の復旧を確認する。紙ウォレットとQRは保存暗号文と同じ形式とは限らないため、形式を一律に置換せず、実際の入出力仕様を個別に確認する。

### P4: 実行基盤の近代化

暗号移行とは別のテーマ群で進める。

1. 依存関係と既知の脆弱性を監査する。
2. 対応するNode.jsとElectronの目標版を決め、Electronのメジャー更新を段階化する。
3. TypeScript、Vue、Jest、ESLintなどを互換性のまとまりごとに更新する。
4. `localStorage` の脅威と運用要件を整理し、Electronでの永続化先とOSの資格情報保護機能の利用可否を検討する。

## 5. 移行の必須条件

- 旧形式を読み取れない版を、移行経路なしに公開しない。
- 移行前の値を保持したまま新形式を保存し、保存と再読込の確認後に切り替える。
- 一部だけ更新された状態を検出し、再試行または復元できるようにする。
- 誤パスワード、認証失敗、破損時には秘密情報を返さない。
- 復号した秘密情報をログ、例外メッセージ、診断データへ出さない。
- 旧形式の読み取りを廃止する場合は、対応版を経由する移行手順とバックアップ手順を先に提供する。
- 保存形式と、紙ウォレット・QRなどの交換形式を区別して互換性を評価する。

## 6. PRの分け方

| 区分 | 内容 | 完了条件 |
|---|---|---|
| 0 | 設計Issue | 脅威モデル、対象範囲、互換性、未決事項、PR順序を合意できる |
| 1 | 現行形式の回帰テスト | テストベクトルと主要な失敗条件が固定される |
| 2 | パスワード変更の整合性 | 全対象鍵を更新でき、途中失敗から復旧できる |
| 3 | 暗号境界 | 現行挙動を維持したまま直接呼び出しを集約できる |
| 4 | 新形式の基盤 | バージョン付き形式と認証暗号を実装し、旧形式も読める |
| 5以降 | 保存対象ごとの移行 | 対象ごとに移行、再起動、失敗復旧を検証できる |
| 別系列 | 実行基盤 | 依存関係や実行環境を、暗号移行と独立して更新できる |

テスト、移行処理、利用箇所の変更は、その成果を成立させるPRに含める。差分の小ささだけを目的に分割しない。

## 7. 実装PRの受け入れ条件

対象範囲に応じて、次を自動テストまたは記録した手動試験で確認する。

- 暗号化と復号
- 正しいパスワード、誤ったパスワード、空値、破損データ
- 新形式の認証失敗と、秘密情報を返さないこと
- 旧形式から新形式への移行
- 保存途中の失敗、再試行、旧データからの復元
- アプリケーション再起動後の復号
- パスワード変更後の全対象秘密情報の復号
- バックアップ、紙ウォレット、QRの往復互換性
- 秘密情報がログや例外メッセージへ出ないこと
- 対象テスト、Lint、型チェック、Webビルド

Electron配布物に影響する変更では、対象OSでの起動と保存データの再読込も確認する。

## 8. 次の作業

1. P0用に、SDK 2.0.6の暗号形式と代表テストベクトルをテストコードへ固定する。
2. パスワード変更について、Harvesting鍵の有無と各保存段階の失敗を含む再現テストを作る。
3. 更新前データの保持方法と、更新完了を確認して切り替える手順を設計する。
4. 現行挙動を変えない暗号サービスの責務とAPIを決める。
5. 以上を公式Issueへ提示できる設計メモにまとめる。
